DevOps Voting App Architecture

A simple view of how code moves from Git to Kubernetes

Application Build Flow

Application Repository Source code, Dockerfiles and Docker Compose
GitHub Actions Builds the application container images
GHCR Stores the built images with commit SHA tags
The application repository is responsible for building images. GHCR stores those images so Kubernetes can pull them later.

GitOps Deployment Flow

Infrastructure Repository Helm chart, values and Argo CD application definition
Argo CD Watches Git and compares it with the cluster
Kubernetes Runs the desired application state
The infrastructure repository does not store container images. It stores the image names and tags that should run. Argo CD reads that desired state, and Kubernetes pulls the selected images from GHCR.

Application Runtime Flow

Browser User submits a vote
Vote Receives the user's vote
Redis Temporarily stores vote events
Worker Processes votes and writes them to the database
PostgreSQL Stores vote data persistently
Result Reads and displays the current result

Kubernetes Workloads

Vote Deployment + Service
Result Deployment + Service
Worker Deployment
Redis Deployment + Service
PostgreSQL StatefulSet + Service + PVC

GitOps Behavior

Auto-Sync A change merged into the infrastructure repository is automatically applied to Kubernetes.
Self-Heal Manual changes in the cluster are corrected so Kubernetes matches Git again.
Prune Resources removed from Git can also be removed from the cluster.
Simple mental model

Application repo → GitHub Actions → GHCR
Infrastructure repo → Argo CD → Kubernetes

The application repository creates the images. The infrastructure repository decides which version should run. Argo CD connects Git to Kubernetes.
